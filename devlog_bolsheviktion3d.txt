3-8-24
	- So I've learnt these entirely new concepts called the accumulator and the fixed timestep, and I've had a bit of a nightmare of a time trying to shoe-horn these concepts into my engine successfully.
	- Right now, the engine is all over the place, it runs but goes into death spirals, is patchy etc.
	- Spent about an hour realising that this code:
	        while (getAccumulator() >= FIXED_TIMESTEP) {
            update();
            deductFromAccumulator(FIXED_TIMESTEP);
        }

	has a fatal flaw: If the accumulator is lower before the first update(), the update function is never called first, and the render function has n othing to update and so hangs.
	My fix:
	    do {
        update();
        deductFromAccumulator(FIXED_TIMESTEP);
    } while (getAccumulator() >= FIXED_TIMESTEP);
	My first ever use case for do-while loops!

	Several Things which elongated the implementation timeframe:
		1) I had to create new texture atlases to accommodate the special characters for each language, and 3 of them for the main char set.
		2) Modern editors encode these strings as UTF-8, in which special non ASCII characters are encoded with 2 bytes. I had to account for the two bytes
		when trying to use the character to look up the atlas position.
		3) Creating new static arrays that correspond with the texture atlas image for all languages.
		4) Creating extra logic to account for the upside down question and exclamation mark.
		5) Refactoring the existing code, removing the inline strings from 1.1 and moving them to a new module, accessed by enum index.
		6) Translating all the strings into different languages and allowing them to be index-looked up.
		7) Connecting the backend settings for language selection on startup.
		8) Accounting for refreshing certain buffers due to the new textures from the language change.
		9) Some strings, which were calibrated tightly for English and fitting correctly into their spaces, run long in the other language.
		10) Considerations needed to be made for multi-language string situations (like a username in Russian)
		11) Other languages, due to different string lengths, needed a slight offset to fit into certain UI elements.
		12) Buffers originally were set up to precisely handle English. Other languages needed tweaking.

	Okay, several things have complicated the smooth rendering I thought I'd fixed yesterday.
	1) To get non-stuttering updates, I need to be able to update the player every frame. But to update the player I need to trigger the update function/
	But, triggering the update function once per moving frame speeds up gameplay, as the update is designed to only be triggered when the accumulator has
	hit its threshold.
	2) The foisting last frame's player.x and player.y starts breaknig some things that update player.x and player.y mid game loop:
		a) We load in a new prevX, prevY at beginning of game loop, then mid game loop logic changes
		or b) when a new level/save etc. is loaded, current X is loaded in as usual, but previous X is kept, and the interpolation of the two messes things up.

	== COMMENT ==
	After much wringing of hands, there is a working interpolation module now.'

	Movement is going too fast because of the following situation:
	In v1.2 movement would sometimes happen, sometimes not, depending on the accumulator.
	But since the accumulator is not a factor in the movement, the player advances every frame if they're
	moving now.
	So I have to devise a way to cap the movement so that it still updates player x, y every frame BUT it takes into account
	the fact that moveemnt is guaranteed every frame.

	Now we're reverting back to basic units per second due to this new requirement. Because my demo storing system only stores the RESULTS of playerMove, new demos
	recorded shouldn't have any further issues.
