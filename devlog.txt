	== COMMENT ==
	Today we're trying a reimplementation of a new gap drawing system.

	deferred draw systemHere's the description of the deferred rendering system.

	KEY CHANGE: Pass in a sentinel integer pointer int* sentinel & float* sentinelDist. Init outside the for loop as -1 and -0.1f respectively.

	1) So we start at one point of the array and start testing and rendering.
	2) When we find something that needs to be deferred to new point in the array, we do all we ned to do, defer, and crucially set the sentinel to that Y point in the array.
	3) Let's say next iteration we also need a defer, well we've already had a sentinel pixel set, so we just defer and keep going.
	4) Let's say we defer 10 more pixels, the sentinel doesn't budge after having first been assigned when a defer came.
	5) finally, deferring finishes. We try to draw the next. BUT we notice that we have an active sentinel number! We cannot draw to the buffer with an active sentinel anything that's not a defer.
	6) This starts to naturally create no ops, and natural gaps, in the buffer.
	7) Let's say now we finally reach the pixel marked by the sentinel. The sentinel then deactivates back to -1, ready to create gaps again.
	8) After normal rendering, we find ANOTHER defer run! On the first pixel, mark the sentinel, keep it marked until the deferral ends, then no op until we see that deferred pixel.
	9) Oh, we reach the top of the screen?No worries, all gravy, no ops to the top.

	We've passed the pain stage, now the insights into the completion of a working prototype of this render engine are starting to coagulate.
	We're now working out the kinks from one module only, with just a few buffer draw functions. Only  a matter of time before the code is cracked for floors and ceils.

	== COMMENT ==
	It's not "misshading" - it's gap filling mechanic on the floor shader which is malfunctioning, specifically "fillDelayBufferGaps"

	Been at this for a few hours now, it's a very subtle bug that hasn't yielded itself to me yet. I have the solution in mind but for some reason, my implementation isn't working.
	The issue is we have a chicken and egg situation. We can't know whether a connector or a gapFill will occur between two planes.

	Here is the problem in detail.
	We have a multi-stage renderer that renders walls->planes->connectors.
	In the plane stage, we have a mechanism whereby we "fill in" missing pixels due to the way we shift floor planes up and down.
	As a result of this mechanism, a draw is made between floor planes of two different heights.
	Now normally, the planes are too far apart for this mechanism to activate.
	But when it gets to a certain distance, the gap between the two planes becomes small enough that the drawer "tweens" in the difference.
	Now usually this wouldn't really be a big deal, but the issue is that the connector phase correctly shades the geometry connecting the two planes.
	And the tweener is not capable of doing that - and so I see this horrible banding at certain distances from stairs etc.

	Now I thought of a few solutions to fix this. I could simply overwrite the plane tweening with the connector. But it seems like it is failing the distance depth check.
	I could swap over the rendering order - render the connectors first then the planes - but I fear that'll mess with carefully tuned depth checks that assumed the order of walls->planes->connectors.

	Interpolater is interpolating distances for these "connectors" as if they were part of the planes - 
	distances get blown out by the lerp and the fact that it's so close to center of screen, 
	so I can't compare them properly to determine which to draw at the connector stage.

	The core issue is that there are two types of "gaps" - one from the limitations of our engine, the other are natural gaps in different floor heights.

	== COMMENT ==
	Today we're going to be fixing some serious immersion breakers in the graphics engine.
	1) low ceiling no op (and floor no op)
	2) Ceiling step lack of granularity.

	In order to do this effectively, instead of starting at the top of the pipeline and working down, I'm going to backward
	from the no op on screen through to where the op is not happening to pinpoint the bug.
	These two specific graphics rendering issues really need a high priority to be resolved today,
	As I due to personal circumstances will not have access to my multi-screen setup to debug live raycasts.

	It looks like it's on the 20% boundary of the screen's Y that the cutoff bug occurs.

	Issue for our ceiling no op is this logic error:

	const int difference = abs(context->y - baselineCeilingY);
	if (difference <= 1) {

	The function only writes ceiling pixels if context->y is within ±1 pixel of baselineCeilingY.

	For y=13 (15% of screen), it's calculating where the baseline ceiling should be, and if y=13 is more than 1 pixel away from that
	baseline, it skips writing entirely.

	When close to a ceiling (walking down stairs), the ceiling extends far from its baseline position, so this check rejects
	it.

	We're going to label this an engine limitation and design levels around it.

	Engine Limitation - Ceiling Plane Rendering:
	- Close proximity to non-standard height ceilings (e.g., walking down stairs under low ceilings) can cause rendering gaps in the
	top 20% of screen
	- Root cause: Ceiling projection lacks above-screen calculation data that floors get via ADD_PIXELS_PERC
	- Workaround: Design stairs/transitions with adequate ceiling clearance or use skybox ceilings in problem areas
	- Fixing would require significant refactoring of plane projection system with performance cost

	After several impactful personal events in my life concurrently, I had an ephiphany, which really was solidified by watching sections of the map get revealed too early in the tab map, is that part of the woes of our overdrawing are
	connected to our framerate issues, and chiefly speaking of the low CPU threading utilisation picked up by vtune. I decided that the proper way forward was to build up a per-ray graph, if you will, showing how far the furthest hit was.
	Then we park in a scene we know should be complete occludedd by walls, and see if we see any unusual spikes int he graph. I built it and sure enough, some massive spikes. Going into the ray visibility algorithm we managed to patch some of them out,
	but frame times didn't increase significantly. I did however buy a 5700X for the development machine, and it 1080p Very High at 24fps, and 17fps while moving as the frameTables need to be constantly recalculated. I don't think there's any way
	around that - it's a very expensive operation to calculate floors and ceilings in this game.

	Despite it not bearing total fruit, I now have seveeral very powerful tools embedded into the mainline game code, which I've now gated behind an undocumented settings.cfg parameter rather than messy ifdef/endif compiler directives.
	This will give us a very powerful ability to quickly debug scenes we see are problematic, hopefully each time saving valuable cycles and thus pushing up CPU time.

	Basically the biggest insight was the fact that if we are waiting on all trhreads to finish at the gate that callThreading provides, then we're constantly held hostage by the slowest col generating pixels. And if we've got rogue cols generating
	more than it needs to, then the frame time is naturally limited by waiting for these slower threads to finish processing. The thinking is if we cut those down/out, then threading can finish earlier and finish processing the frame
	earlier.

	Anzer Crypt is going to be the 3rd secret level of Bolsheviktion 3D 2. It's going to Be our attempt at doing a Doom level, using all of Romero's level design tips.

	ROMERO'S LEVEL DESIGN RULES
	---------------------------
	1. Always change floor height when changing floor textures
	2. Use special border textures between different wall segments and doorways
	3. Be strict about texture alignment
	4. Use contrast everywhere in a level between light and dark areas, cramped and open areas
	5. Make sure that if a player could see outside that they should be able to somehow get there
	6. Be strict about designing several secret areas on every level
	7. Make the level flow so the player will revisit areas several times so they will better understand the 3D space of the level
	8. Golden rule of level design – the “Horseshoe” layout
	9. Build your first level last
	10. Don’t constrain player movement (aka don’t let detailing get in the way of gameplay)
	11. Use fullbright textures
